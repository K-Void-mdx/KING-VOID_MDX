# 8. `.chatbot on/off`

This is the main automatic AI mode.

When chatbot mode is ON, NOVA_VOID should respond when the bot is explicitly addressed.

### Trigger A — direct mention

Example:

```text
Member: @NOVA_VOID hey hi
```

Expected behavior:

```text
NOVA_VOID: Hey there 👋 How can I help you?
```

### Trigger B — WhatsApp reply/swipe

Example:

```text
Member replies/swipes to a message sent by NOVA_VOID:
what did you mean?
```

Expected behavior:

NOVA_VOID responds using the AI system.

### Non-trigger

Example:

```text
Member: hey everyone 😂
```

NOVA_VOID must stay silent.

### Critical implementation requirement

Do NOT detect mentions by simply searching the message text for `@`.

Use actual WhatsApp/Baileys metadata:

- `mentionedJid`
- quoted/replied message participant
- bot JID
- normalized message context

The chatbot should only trigger when:

```text
DIRECT_MENTION(bot)
OR
REPLY_TO_BOT(bot)
```

---

# 9. `.train`

`.train` is persistent bot knowledge/personality/memory.

It is **not model fine-tuning**.

It should allow the owner to teach NOVA_VOID things such as:

- name
- creator
- personality
- preferred responses
- facts about the bot
- custom knowledge
- instructions
- project-specific information

Example concept:

```text
.train add creator My owner is ...
```

The exact final syntax may be refined later, but the system must support:

- add
- update
- list
- remove
- persistent storage

Training data is separate from conversation history.

---

# 10. CONVERSATION HISTORY

Conversation history is temporary/session context.

Example:

```text
User: Who is Elon Musk?
Bot: ...
User: How old is he?
Bot: ...
```

The second message can use the first message as context.

History must be scoped to an authorized session.

Do not expose one user's AI conversation to another user.

Do not send unrelated group conversation to the AI provider.

History should have configurable limits so it does not grow forever and consume excessive API tokens/storage.

---

# 11. `.history`

`.history` should provide authorized users with access to their current AI session/history.

Possible future behavior:

```text
.history
```

returns a compact summary or controlled view.

The command must respect permissions.

Owner and approved paired/session users may have access according to the final permission policy.

---

# 12. `.clear-h`

`.clear-h` clears the current user's/session's conversation history.

It must **not** delete persistent `.train` knowledge.

---

# 13. `.clear-h all`

This is an owner-only operation.

It clears all stored AI conversation histories.

It must not accidentally erase:

- bot configuration
- training memory
- user accounts
- group settings

---

# 14. `.generate`

The user wants image generation similar in concept to Meta AI, Gemini, or ChatGPT image generation.

Example:

```text
.generate a futuristic black spaceship above Lagos at night
```

The architecture should support an image-generation provider without coupling the entire bot to one API.

Video generation is desirable later.

Do NOT promise:

- unlimited free generation
- unlimited free video generation
- permanent availability of any free API

Provider availability, quotas, pricing, and commercial rights must be checked before selecting a production provider.

# 15. AI ARCHITECTURE

The AI system should be unified.

Do NOT create independent hard-coded AI systems for every command.

Target architecture:

```text
src/ai/
├── provider.js
├── router.js
├── session-store.js
├── memory.js
├── chatbot.js
├── generate.js
└── prompts.js
```

Responsibilities:

### `provider.js`

Defines the provider contract and provider-specific error abstraction.

### `router.js`

Selects providers and handles fallback.

### `session-store.js`

Stores temporary conversation sessions.

### `memory.js`

Stores persistent `.train` knowledge.

### `chatbot.js`

Determines whether an incoming message actually triggers chatbot mode.

### `generate.js`

Abstracts image/video generation providers.

### `prompts.js`

Builds system/personality/training prompts.

# 16. PROVIDER STRATEGY

The user has mentioned that free API keys may be available later.

The architecture must therefore be provider-neutral.

Rules:

- Never hard-code provider credentials.
- Never commit API keys.
- Use environment variables/secrets.
- Allow multiple providers.
- Allow fallback.
- Keep provider-specific request/response formats inside adapters.
- Keep command code provider-independent.
- Limit prompt/history size.
- Do not send unnecessary group data.

Potential providers can be researched later based on current availability, free quotas, latency, model quality, and commercial terms.

Never assume an API is free forever.

# 28. SECURITY FINDINGS FROM THE OLD PROJECT

The audit found several issues that must not be copied forward.

### Hard-coded credentials

Old configuration contained credential-like/API values.

NOVA_VOID must never commit real keys.

### Giant eval/shell capabilities

Dangerous capabilities existed in the old message system.

### Updater

NOVA_VOID should use a predictable release-based updater later.

### Session data

WhatsApp authentication files must remain outside Git.

# 54. FINAL PRODUCT DEFINITION

NOVA_VOID MDX is intended to become:

> **A clean, modular, Termux-friendly WhatsApp bot with roughly 150–180 useful commands and a compact but genuinely useful AI assistant.**

The AI assistant should:

- answer when mentioned
- answer when replied to/swiped to
- remain silent during ordinary group conversation
- support one-off AI requests
- remember authorized conversation context
- support owner-controlled training/personality
- allow history viewing/clearing
- support image generation through pluggable providers
- optionally support video generation later

The bot should be:

- maintainable
- secure
- lightweight where practical
- easy to configure
- extensible
- commercially auditable
