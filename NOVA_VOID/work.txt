AI SYSTEM — USER REQUIREMENTS
-----------------------------
The AI should be intentionally SMALL and useful, not a huge collection of AI commands.

Required AI features:

1. .chatbot on/off
   - When ON, NOVA_VOID replies only when directly mentioned/tagged OR when the incoming WhatsApp message is a reply/swipe/reply-to a message sent by NOVA_VOID.
   - Example mention:
       Member: @NOVA_VOID hey hi
       NOVA_VOID: Hey there 👋 How can I help you?
   - Example reply:
       Member replies to NOVA_VOID's previous message: what do you mean?
       NOVA_VOID replies using AI.
   - Ordinary group conversation must NOT trigger the AI.
   - Trigger detection must use actual WhatsApp/Baileys message context/metadata, not a naive text-only @ check.
   - Respect group/private settings and permissions.

2. .train
   - Owner-controlled persistent bot knowledge/personality/memory.
   - This is NOT model fine-tuning.
   - Training data should be stored separately from temporary conversation history.
   - Owner can add/update/remove/list training knowledge as the command design evolves.

3. .ai <prompt>
   - Optional one-off AI request.
   - Uses the same unified AI provider/router as chatbot mode.

4. .history
   - Shows/handles conversation history for the current authorized session.
   - Owner and approved paired/session users may have access according to permission rules.
   - Do not expose another user's AI history.

5. .clear-h
   - Clears the current session's AI conversation history.
   - Must NOT erase persistent .train knowledge.

6. .clear-h all
   - Owner-only global history reset.

7. .generate <prompt>
   - Image generation is desired, similar in concept to Meta AI/Gemini/ChatGPT image generation.
   - Video generation is desirable if a suitable provider/API is available later.
   - Do not promise unlimited free video generation.
   - Build provider adapters so image/video providers can be added without rewriting the AI core.

AI ARCHITECTURE
---------------
Use one unified AI system rather than separate hard-coded API implementations for each command.

Target structure:

ai/
  provider.js       # provider contract/interface
  router.js         # choose provider/model and fallback strategy
  session.js        # conversation sessions/history
  memory.js         # persistent .train knowledge
  chatbot.js        # mention/reply trigger behavior
  generate.js       # image/video generation abstraction
  prompts.js        # system/personality prompt construction

Provider credentials belong in environment variables or secret storage only.
Example placeholders in .env.example are acceptable; real keys must never be committed.

AI PROVIDER REQUIREMENTS
------------------------
- Provider agnostic.
- Support multiple providers later.
- Allow a fallback provider if the preferred provider fails or reaches limits.
- Do not hard-code one gateway.
- Keep provider-specific response formats behind adapters.
- Keep AI command code thin.
- Store only necessary history/context.
- Provide configurable history limits to avoid excessive token/API usage.
- Do not send full unrelated group history to an AI provider.
- Be privacy-conscious with stored conversations.

COMMAND SYSTEM
--------------
Target approximately 150–180 useful commands, with an upper preference of about 200.

The goal is quality and clarity, NOT command-count inflation.

Suggested categories:
- AI: ~7–10
- Owner: ~15
- Admin: ~20–25
- Group: ~20
- Downloader: ~15–20
- Media: ~10–15
- Utility: ~15–20
- Search: ~8–10
- Fun/Games: ~10–15
- Converter: ~8–10
- System/Help: ~10

Every old command must be classified:
- KEEP — useful and healthy
- REWRITE — useful but poor implementation
- MERGE — duplicates another command
- REMOVE — broken, pointless, unsafe, or unnecessary
- NEW — required by NOVA_VOID but absent

Do not port commands automatically.

PERMISSION MODEL
----------------
Simplify the old owner/sudo/admin model into a clear hierarchy:

OWNER
  -> TRUSTED/SUDO
  -> PREMIUM (future commercial tier)
  -> ADMIN
  -> USER

Owner-only operations must be enforced centrally, not trusted to individual command authors.

WHATSAPP CORE
-------------
The old project mixes connection handling into a large obfuscated engine.

NOVA_VOID should isolate:

WhatsAppConnection
  connect()
  reconnect()
  logout()
  pair()
  event handling

Message normalization should produce a consistent context object for every message, including:
- chat/group id
- sender
- participant
- message id
- text/body
- command/prefix
- mentioned JIDs
- quoted/replied message metadata
- whether the message is a reply to NOVA_VOID
- group metadata
- sender/admin/owner permissions

CHATBOT TRIGGER RULE
--------------------
With chatbot enabled:

TRIGGER = direct mention OR reply-to-NOVA_VOID

NOT A TRIGGER = normal message without mention/reply

Do not use a broad 'contains @' rule because that can trigger on arbitrary text.

DATABASE/STORAGE
----------------
The old project has basic runtime JSON storage but does not provide the clean data model needed for the new AI system.

Target concepts:

storage/
  config/
  users/
  groups/
  sessions/
    ai/
  memory/
  cache/

Separate:
- temporary AI conversation history
- persistent .train knowledge
- user settings
- group chatbot settings
- bot configuration

.clear-h clears conversation history only.
.clear-h all is owner-only and clears all conversation histories.
.train data survives history clearing.

- avoid duplicate media/downloader libraries

SECURITY
--------
Known old-project concerns:
- credential-like values/API secrets existed in configuration/source
- updater could download/copy/delete files in ways unsuitable for a commercial product
- giant eval/shell/owner functionality needs careful permission isolation

NOVA_VOID rules:
- no real secrets in Git
- .env ignored
- .env.example placeholders only
- rotate old exposed credentials if they are still active
- owner/admin dangerous commands must be centrally protected
- never allow ordinary users to execute arbitrary shell/eval
- validate downloaded media/files
- limit AI request size and rate
- limit history size
- log security-sensitive actions
